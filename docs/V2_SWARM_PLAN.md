# Zokul v2.0: рой агентов — план к старту

Статус: **подготовлено, ждёт команды владельца на старт** (2026-10-23).
Короткая версия цели — в `docs/ROADMAP_V1_V2.md`, раздел «Версия 2.0».

## Что это

Команда ИИ-агентов с ролями работает над задачей в комнате Zokul, рядом с людьми.
Агенты делят работу, передают её друг другу и проверяют друг друга. В контрольных точках
они останавливаются и ждут «да» человека. Человек — руководитель: ставит задачу,
одобряет, может остановить всё одной кнопкой.

Это **не** один автономный агент «сам себе начальник». Ничего важного не происходит без человека.

## Главное архитектурное решение

**Боты роя — обычные агенты Zokul.** Каждый бот — это агент со своим ключом `zk_…`,
который ходит в существующий API агентов (`/api/agent/*`). Отдельный сервис `swarm`
(свой контейнер) держит ключ модели, гоняет модели и решает, кто ходит следующим.

Почему так:
- все границы безопасности уже есть и проверены: агент видит только свои комнаты,
  не может управлять участниками, не попадёт в админку, его ключ отзывается (20 атак симуляции);
- ключ модели (OpenRouter) живёт только в `.env` сервиса `swarm`, никогда в базе, чате или браузере;
- рой можно выключить, не трогая мессенджер: остановили контейнер — мессенджер работает дальше;
- те же карточки (статус, вопрос, передача) уже понятны людям и работают на телефоне.

```
люди (браузер/телефон) ──► Zokul server ◄── API агентов (zk_ ключи) ── swarm runner ──► OpenRouter (бесплатные модели)
                                │                                          │
                         PostgreSQL / Redis                      состояние запусков (таблицы swarm_*)
```

## Чего не хватает в v1 (проверено 2026-10-23)

API агентов сейчас умеет только **писать**: `status`, `messages`, `questions`, `handoffs`, `chats`.
Для роя нужно:
1. **Читать комнату:** `GET /api/agent/chats/:id/messages?since=…` — только чаты, где агент участник.
2. **Входящие:** `GET /api/agent/inbox?wait=30` — длинный опрос: @упоминания агента, ответы на его вопросы,
   передачи в его комнатах. Без него бот не узнает, что к нему обратились.
3. MCP-инструменты для этого: `zokul_read_messages`, `zokul_wait_inbox` (полезно и обычному Claude Code в v1).
4. **Сообщения от людей для бота — данные, не команды.** Чтение отдаёт текст с пометкой автора
   (человек/агент), runner кладёт его в промпт в отдельном блоке «сообщения команды».

## Модель данных роя (новые таблицы, миграции как в v1)

- `swarm_roles` — карточка роли: название, характер, системный промпт, разрешённые действия, модель, лимиты.
- `swarm_runs` — запуск: комната, задача, кто запустил, состояние (`planning → working → review →
  awaiting_approval → done | stopped | failed`), бюджет и расход (шаги, токены, время).
- `swarm_steps` — каждый ход бота: роль, вход (ссылки на сообщения), ответ модели, действие, длительность.
  Это журнал «почему бот так сделал».

## Безопасность и контроль (обязательно с первого среза)

- **Лимиты на запуск:** максимум ходов, токенов, времени; по исчерпании — пауза и вопрос человеку.
- **Стоп-кран:** кнопка «Остановить» на карточке задачи и команда `/stop` в комнате. Останавливает все боты запуска сразу.
- **Защита от зацикливания:** если боты обменялись N сообщениями без человека — пауза.
- **Узкие права ролей:** бот делает только действия своей роли (например, ревьюер не публикует).
- **Контрольные точки:** перед любым действием «наружу» (публикация, Telegram, отправка файла) — карточка-вопрос,
  действие выполняет runner, а не модель, и только после «да».
- **Бесплатные модели имеют жёсткие лимиты частоты:** runner ставит запросы в очередь и повторяет с паузой,
  а не долбит API.
- **Журнал:** запуск, остановка, одобрение, каждый ход — в `audit_log` и `swarm_steps`.
- **Тесты:** модель-заглушка (детерминированные ответы) для автотестов и симуляции; настоящие модели — только вручную.

## Срезы (каждый — рабочий результат, тесты, проверка вживую, коммит)

1. **Агенты читают комнату.** `messages` для агента + `inbox` с длинным опросом + MCP-инструменты.
   Тесты прав: чужие комнаты закрыты. Расширить симуляцию: агенты реагируют на @упоминания.
2. **Каркас runner'а.** Контейнер `swarm` в `docker-compose.*.yml`, клиент OpenRouter, модель-заглушка,
   одна роль, лимиты, стоп-кран, таблицы `swarm_*`. Без ключа работает на заглушке.
3. **Роли и этапы.** Несколько ролей, машина состояний запуска, ревью ботом, вопрос человеку на чек-пойнте.
   В интерфейсе — карточка «Задача команды»: этапы, кто сейчас работает, расход бюджета, кнопка «Остановить».
4. **Демо-сценарий.** «ИИ-редакция»: исследователь, автор, редактор, фактчекер готовят пост;
   публикация (например, в Telegram) — только после «да» владельца. Альтернатива — «дев-команда»
   (аналитик, разработчик, тестировщик, ревьюер) над задачей из чата.
5. **Испытание роя.** Симуляция: инъекция промпта в сообщении человека, бесконечный спор ботов,
   исчерпание бюджета, падение модели, стоп посреди хода. Всё должно останавливаться предсказуемо.

## Что понадобится от владельца в момент старта

- **Ключ OpenRouter** — владелец сам кладёт его в `.env` сервиса `swarm` (`OPENROUTER_API_KEY=…`).
  Не присылать в чат. До этого всё работает на модели-заглушке.
- **Выбор бесплатных моделей** — список бесплатных моделей меняется, поэтому сверяем актуальный на старте.
- **Какой демо-сценарий первым:** «ИИ-редакция» или «дев-команда».
- **Публикация наружу (Telegram)** — нужна ли в демо.

## Готово к старту (база v1)

- API агентов, карточки статус/вопрос/передача, «Беру» для людей, MCP + CLI — работают и покрыты тестами.
- Безопасность: только по приглашениям, владелец один с 2FA, сессии рвутся при блокировке, 20 атак отбиты.
- Проверка: 127 тестов сервера, 30 тестов интерфейса, симуляция компании (`scripts/sim`),
  визуальная проверка одной командой (`scripts/qa`, `npm run visual`), живые проверки 2FA и аккаунтов.
- Данные: ежедневные резервные копии (сервис `backup`), проверка восстановления `scripts/test-restore.sh`.
